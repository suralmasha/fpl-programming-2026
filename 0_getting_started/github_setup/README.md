# Правила слияния PR

Материалы в папке:

| Файл                   | Куда подключить                                                  |
|------------------------|------------------------------------------------------------------|
| `checks.yml`           | Скопировать в `.github/workflows/checks.yml` своего репозитория. |
| `main-rules.json`      | Импортировать в настройках GitHub.                               |
| `exam-base-rules.json` | Импортировать в настройках GitHub.                               |

## Подключение

Настройку выполняет владелец репозитория.

1. Создайте **публичный** репозиторий с README и веткой `main`. Пригласите участников и преподавателя `suralmasha`; все принимают приглашения.
2. Создайте `exam-base` от стартового коммита `main`. Эта ветка остается ПУСТОЙ: код и workflow добавляйте только в `main` и рабочие ветки.
3. Добавьте `checks.yml` в `.github/workflows/checks.yml` своего репозитория в `main`. **Важно!** Python в workflow должен соответствовать проекту (по умолчанию 3.12).
4. Дождитесь зеленой проверки `project-tests` во вкладке `Actions`. Пока тестов нет, она завершится успешно с сообщением об их отсутствии.
5. Откройте `Settings` → `Rulesets` → `New ruleset` → `Import a ruleset`. Выберите `main-rules.json` и сохраните кнопкой `Create`. Аналогично импортируйте `exam-base-rules.json`.
6. У обоих правил должен быть статус `Active`, а список `Bypass list` должен быть пустым.

JSON нужно именно импортировать: добавление файла в репозиторий само по себе правила не включает.

## Что гарантируют правила

- Изменения в `main` можно вносить только через PR, прямой push запрещен
- Для слияния PR требуется как минимум один `Approve` от другого участника с правом записи; закрыты обсуждения кода; пройдены `project-tests` и `pr-content`
- Описание PR содержит текст; одобряющее ревью текущей версии содержит непустой итоговый комментарий
- После новых изменений нужно повторное одобрение, и `project-tests` и `pr-content` должны пройти снова
- В ветке `exam-base` запрещены обновления, слияния, удаление и force push

Итоговый PR (экзаменационная версия) `submission` → `exam-base` нужно будет создать перед экзаменом и оставить открытым.

## Описание PR и итог ревью

В описании PR напишите, что изменено и как проверено. Пустое описание не засчитывается.

Ревьюер пишет итог в поле комментария при отправке `Approve`: что проверил, что запускал и есть ли замечания.
Пустой `Approve`, комментарий автора PR и отдельные комментарии к строкам не заменяют итог одобряющего ревью.
Нужно хотя бы одно такое одобрение от другого участника с правом записи для текущего коммита PR.

Проверка `pr-content` обновляется при изменении описания, кода, отправке, редактировании или отзыве ревью.
До первого одобрения она будет красной - это ожидаемо. Проверка отсеивает пустой текст, но не оценивает его содержательность.
Задание `content` читает данные через API GitHub и не запускает исходный код проекта; отдельное задание `tests` запускает тесты с правом только на чтение репозитория.
Работайте в ветках общего репозитория, как описано в правилах курса.

Самостоятельное отключение проверок в своем репозитории делает весь PR незачтенным.

## Как запускаются тесты

Workflow выбирает окружение по файлам в корне: `poetry.lock` / `uv.lock` / `requirements.txt` / устанавливаемый проект с `pyproject.toml`.
Для Poetry и uv добавьте `pytest` в стандартные зависимости разработки (группа `dev`) и обновите lock-файл. При дополнительных группах зависимостей скорректируйте шаг установки.

Запускается весь набор pytest согласно настройкам проекта. Код 5 означает, что тесты не найдены, и пока разрешает слияние. Падение теста, ошибка импорта, сбора или установки зависимостей блокируют слияние. Используйте стандартные имена `test_*.py` или `*_test.py`.

- [параметры правил](https://docs.github.com/en/rest/repos/rules#create-a-repository-ruleset)
